# 工作流设计规范

## 先描述行为

新流程先定义目标、服务范围、入口事件、阶段、成功结果和拒绝/失败边界，再写Prompt。不要预设每个项目都要留资、建群、固定追问次数或静默。

每项修改有“改动项 / 保留项 / 影响范围 / 验收行为”。区别模型理解错、事实已提取但状态未更新、回复与路由不一致、参数格式错误、工具未执行、工具执行失败与前端渲染错误。

## 节点表

| 节点名称 | 类型 | 输入 | 条件或职责 | 输出 | 后续/失败路径 |
|---|---|---|---|---|---|
| 判断｜资料是否齐全 | 条件分支 | 项目确认的资料字段 | 按已确认门槛分流 | 对应分支 | 缺项/完整/无效 |

采用“阶段｜动作/对象”，例如“入口｜识别请求类型”“资料｜提取客户信息”“推送｜提交外部系统”。这是命名示例，不是必须加入的业务节点。

标题避免无意义序号、历史版本堆叠和模糊“特殊守卫”。节点描述简短回答为什么存在、读取什么、改变什么、成功/异常去哪。保留稳定内部ID，只有确认引用和平台兼容后才迁移ID。

## 变量设计

| 字段 | 应说明的内容 |
|---|---|
| 名称与中文含义 | 语义明确，遵守已有接口契约 |
| 类型与允许值 | 区分字符串"0"、数值0、布尔值、空字符串和null |
| 默认与生命周期 | 本轮输出、会话持久化、应用配置，何时初始化/重置 |
| 写入职责 | 哪个节点/互斥入口可写，更新规则是什么 |
| 读取用途 | 哪些条件、回复和工具使用 |
| 必要性 | 不能直接复用已有字段或节点输出的原因 |
| 迁移兼容 | 老会话缺值/旧值如何处理，是否需要回滚兼容 |

事实（客户说了什么）、流程进度（下一步做什么）、执行结果（外部动作成功与否）分开。避免多个字段同时表示“已经完成”却由不同逻辑更新。允许有不同业务维度，不能为了变量少而把无关状态塞成一个大JSON字符串。

不机械把所有状态判断改成条件节点；选择已验证且符合复杂度的实现。也不把应由程序确认的外部调用结果交给模型猜测。

## 连线与布局

- 主路径统一从左到右或从上到下；同阶段成组，异常路径靠近操作下方/侧方。
- 条件用业务含义表达；平台不支持边标签时，在分支条件和节点描述中补充清楚。
- 汇合节点说明选哪个来源、来源互斥条件、未执行分支如何处理。不可依赖上一轮残留输出。
- 尽量减少交叉和长距离折返；通过分区与合理位置调整改善，不为美观额外增加业务状态。
- API保存的坐标不等于视觉检查通过。可用且获准时检查画布；否则明确“仅做布局数据检查”。

## 模型与Prompt

每个模型有输入来源、职责、输出约定、禁做事项与失败处理。公共规则只维护一个权威来源，分支补充自身差异；纠正原规则，不在末尾反复叠加相反指令。

追问选择与回复组织共享同一决定；保存真正发出的追问。业务事实每轮更新但已接受的值不被无关输入清空。新需求何时重置状态由项目规则决定。

模型选择依赖现有可用服务、效果、成本、延迟和结构化输出支持，不硬编码某品牌模型。模型/温度/输出方式的变更也可能改变业务判断，须计入影响范围。

## 输出与副作用契约

结构化输出明确键、类型、缺失值、最大长度及消费者。模型输出JSON文本不是程序级保证。若采用模型格式审查，必须标注概率性、增加的调用和未接住的异常，不能称为严格校验。

校验能力先核实，再设计有限重试与失败出口。避免长文本反复嵌套转义。签名、字段格式或去重方式要变更时单独分析兼容，不顺带修改。

外部动作区分资格完整、未调用、调用中、已确认成功、已确认失败、结果未知。不得因HTTP200就声称业务成功；结果未知时先查事件或幂等记录，再考虑重试，不盲目重复发线索/建群/付款。

## 复杂度预算

在设计和候选完成时各检查一次：最长路径、分支数、模型串行调用、状态数量、输出尺寸、工具延迟。嵌套循环/迭代须按平台实际计数，不能仅看全图节点总数。

超过限制不能自动删业务、绕过校验或修改平台全局限制。提出等价合并或受支持的封装方案，说明行为不变依据及验证要求。
